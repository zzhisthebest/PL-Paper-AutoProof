# Baseline 证明过程核查记录

对象：`gpt6luna_high_difficulty_v4_full_r1`，33 道超时题。此文补充过程证据，不以最终缺哪个引理代替原因。

## 读法与统计口径

每行记录模型做了什么、遇到什么问题、怎样修改、修改后走到了哪里。`L` 是原始 JSONL 的行号，不是源码行号或时间。原始记录路径为：

`benchmarkResults/<case>/traces_gpt6luna_high_difficulty_v4_full_r1/<case>.jsonl`

[原有 108 题附件](baseline-trace-analysis-2026-10-20-cases.md)提供各题 trace 和最终源码链接。过程核查结合了模型说明、实际命令、打印出的源码片段和编译目标；说明中的“已完成”不单独作为证据。

“检查数”是指定日志区间内，已完成的命令中包含 `coqc` 或 `rocq compile` 的条数，与该题总数的对照。它衡量检查活动，不等于报错次数、返工次数或耗时；例如辅助引理通过后，整文件仍会因目标留空而返回错误。日志没有逐事件时间戳，不能将这些比例换算成“花了多少分钟”。

按实际工作过程划分：

- **方案返工（20 题）**：改变 LR、核心命题或所需的条件后，又调整相应证明。包括条件写错、条件不足、递归定义不被 Rocq 接受，以及原命题不够一般。
- **较弱结论（6 题）**：大量工作完成的是普通类型、初始可执行性或已经是值的程序的性质；目标还需要运行过程中保持条件。后者没有随前者获得。
- **具体证明（6 题）**：能观察到连续实现具体证明、修复调用和表达式转换，但没有完成；不是凭最后一个报错断言整个数学方案有问题。
- **后段停滞（1 题）**：后段重复确认同一核心缺口，增加少量特殊情况，没有形成一般证明。

每题归入最能描述其过程的一项，不表示其他问题不存在，也不是“改掉这一项就必成功”的实验结论。
