第 178–397 行：推演 fundamental 如何处理 lambda 的 body。
拟用 substitution 把 body 中的新鲜自由变量换成实际参数，同时比较“直接约束 application”和“约束归约到的 value”的 LR 写法。还在考虑 local closure 和相关辅助引理。

第 398–528 行：尝试用直接约束 application 的 LR 打通主证明。
这种 LR 让 APP 分支可以直接使用定义；lambda 分支则需要从“代入后的 body 满足 LR”推出“整个 lambda application 满足 LR”。模型推演对参数的 SN 归纳，但部分论证仍混用了另一版 LR 的条件。

第 529–888 行：为 LR 加入 local closure，并安排辅助引理。
发现证明 reduction closure 时，ST_App1 需要参数 locally_closed，因而将该条件加入 LR。继续推演 reduction closure、lambda application、typing/local closure 和 substitution 等引理，以及 fundamental 的组合方式。

第 889–1335 行：在嵌套 application 上遇到困难，重新比较路线。
在推演 lambda application 引理本身的证明时，展开 arrow 返回类型的 LR，产生了嵌套 application 子目标。尝试按返回类型归纳时，设想的归纳假设仍只覆盖“lambda 直接接收参数”的形状，不能直接处理“application 的结果再接收参数”的形状。（这是引理内部的证明困难，不是已经证明好的引理无法用于 fundamental。）于是重新考虑 value/reduction-based LR、较弱的 SN 条件、更一般的辅助引理和递减 measure，也多次回忆教材证明；没有在这一段落实替代路线。

第 1336–1597 行：尝试 value 限制，引出 backward closure。
考虑将 arrow 条件限制为 value 参数，以简化 lambda 分支；但这样 APP 分支又需要处理非 value 参数。随后尝试 backward closure：由各个一步后继满足 LR 推回原程序满足 LR，并发现必须排除 abstraction。再考虑用这个引理支持不限制 value 参数的原 LR。

第 1598–1729 行：补齐 backward closure 的归纳结构。
为处理参数继续 step 的情况，在按 type 归纳之外，再对参数的 SN 证明归纳；据此推演 lambda application 引理。随后开始列出 freshness、substitution 等辅助定义和证明。此时认为核心路线可行，尚未编译。

第 1730–1801 行：发现 substitution/opening 缺少 local closure 前提。
检查自由变量分支时，发现替换项中的悬空 index 会被后续 opening 改动，等式不能无条件成立。又发现环境条件只约束环境里的变量，于是给 fundamental 增加“所有替换项 locally_closed”的前提。
<p style="color: #2563eb;">这里就是我亲自遇到的问题：替换项如果不是 locally_closed，后做的 opening 可能改动其中的悬空 index。这段思考是在补齐必要条件，这是resonable的。</p>

第 1802–2437 行：重新检查完整路线，并展开 proof 的写法。
围绕已选 LR，逐步推演 backward closure、lambda application、fundamental 和最终 normalization。反复检查归纳假设、freshness、substitution 等式、inversion 后的 hypothesis 和 tactic 的执行顺序。

第 2438–3624 行：继续在思考中草拟和检查代码。
写出多段辅助引理与主证明草稿，调整 generalization、参数、命名、rewrite 的 side condition 和文件插入方式。多次表示准备编辑，但仍继续推演。最后将 LR 命名为 Red，保留“local closure + SN + application 满足返回类型 LR”的核心定义。
